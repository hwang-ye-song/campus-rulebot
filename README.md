# 한양 챗봇

> 학칙을 근거로만 답하는 ERICA 학사 상담 AI
> 2026학년도 AI 활용 학사제도 개선 아이디어 공모전 출품작

학생의 질문은 밤에도 생기는데, 답할 수 있는 창구는 낮에만 열려 있습니다.
그 공백을 지금은 익명 커뮤니티가 메우고 있고, 거기엔 근거도 책임도 없습니다.

---

## 왜 만들었나

### 1. 질문의 시각과 응답의 시각이 어긋나 있다

학사 문의는 행정실이 열린 시간에만 생기지 않습니다. **수강신청 전날 밤, 정정 기간 마지막 날 밤,
휴학을 고민하는 새벽**처럼 운영시간 밖에도 계속 생기고, 기한을 앞둔 결정일수록 더 그렇습니다.
그런데 답할 수 있는 창구는 **평일 낮에만** 열려 있습니다.

학사 결정에는 되돌릴 수 없는 기한이 붙어 있습니다. 수강신청 정정 기간, 다전공 신청 마감,
휴학·복학 신청 시한은 하루만 지나도 다음 학기로 밀립니다.
그래서 학생은 기다리는 대신 **다른 곳에 묻습니다.**

### 2. 그런데 학칙은 스스로 답하지 않는다

"규정이 모호하다"는 인상이 아니라 계측의 대상입니다.
한양대학교 학칙(2024.10.31. 개정) 전문 61쪽을 조문 단위로 분해해 측정했습니다.

| 항목 | 건수 |
|---|---|
| 전체 조문 | **87개 조** |
| "따로 정한다 · 별도로 정한다" (타 규정 위임) | **60건** |
| "다만, …" (단서 · 예외) | **71건** |
| "~할 수 있다" (재량 표현) | **86건** |

조문이 87개인데 다른 규정으로 넘기는 문구가 60건입니다.
학생이 학칙을 펼치면 상당수의 조항에서 **"세부사항은 따로 정한다"** 를 만나고,
그 "따로"가 어느 문서인지는 학칙이 알려주지 않습니다.

가장 극단적인 사례는 **제49조(복수전공, 다중전공)** 입니다. 조항 세 개 항이 전부 위임입니다.

> ① 복수전공 이수 희망자는 총장의 승인을 받아 복수전공을 이수할 수 있다. **복수전공에 대한 세칙은 따로 이를 정한다.**
> ② 다중전공 … **다중전공에 관한 세칙은 따로 이를 정한다.**
> ④ … 이에 대한 **세부사항은 따로 정한다.**

이수 학점도, 신청 자격도, 포기 절차도 학칙에는 없습니다.

### 3. 그리고 같은 질문에 정답이 여러 개다

**"23학점 들을 수 있나요?"** — 학칙 제33조는 "20학점을 초과하지 못한다"고만 적혀 있습니다.
실제 적용은 이렇게 갈립니다.

| 학적 조건 | 수강 가능 최대 학점 | 23학점 신청 |
|---|---|---|
| 25학번 이하 · 단일전공 | 20학점 | **불가** — 3학점 초과 |
| 25학번 이하 · 다전공자가 타 학과 전공 수강 | 20 + 3 = **23학점** | **가능** |
| + 사회봉사 신청 / + ROTC 필수 교과목 | 각각 +1 / +2 | 여유가 더 생김 |
| 26학번 이후 · 1·2학년 / 3학년 이상 | 20학점 / **18학점** | 둘 다 불가 |
| 약학과 / 스마트융합공학부 | 22학점 / **23학점** | 스마트융합공학부만 가능 |

여기에 **시점**까지 얽힙니다. 안내문은 *"개강 후 정정기간에 학과 이수제한이 풀리니
이때 시도해보시길 바랍니다"* 라고 적는 반면, 교차수강신청은 *"정정기간에는 수강 취소만 가능"*,
교직과목은 *"수강신청 시 정정기간 수강 취소가 됨"* 입니다.
**같은 강좌가 시점에 따라 신청 가능과 불가능으로 뒤집힙니다.**

상한을 넘기거나 최소학점에 미달하면 **수강신청 전부가 무효화되고 해당 학기 평점이 0.00으로
처리**됩니다. 규정을 잘못 아는 비용이 곧바로 학점으로 돌아옵니다.

**학적정보 없이는 누구도 이 질문에 정확히 답할 수 없습니다.**
익명 커뮤니티가 특히 잘 틀리는 지점이 바로 여기입니다.

## 무엇을 만들었나

### 설계 3원칙

**① 근거 없으면 답하지 않는다**
규정 원문에서 근거 문단을 찾지 못하면 답변을 생성하지 않고,
학사운영팀 전화 안내와 1:1 문의 접수로 넘깁니다. 모른다고 말할 수 있어야 나머지 답변이 신뢰를 얻습니다.

**② 답변에 조항을 붙인다**
모든 답변에 문서명과 조항 번호를 표시합니다.
모델이 인용한 조항 번호가 실제로 전달한 조문에 있는지 대조한 뒤에만 근거로 인정합니다.

**③ 학적정보로 답을 확정한다**
학번·학년·전공 유형·추가 신청 사항을 반영해 그 학생에게 적용되는 값만 계산합니다.
시연에서는 다섯 가지 프리셋으로 조건을 바꿔가며 답이 갈리는 것을 확인할 수 있습니다.

실제 운영 시에는 로그인과 동시에 **학사정보시스템과 수강신청 시스템 양쪽에서** 불러옵니다.
학적정보만으로는 부족합니다. *"이 수업 지금 신청할 수 있나요?"* 에 답하려면
**현재 신청 학점, 강좌별 이수제한, 여석**까지 필요하고, 여기에 **신청 시점**(개강 전인지
정정기간인지)이 더해져야 합니다. 정정기간에는 학과 이수제한이 풀리는 반면
교차수강신청은 취소만 가능해지는 식으로 규칙이 뒤집히기 때문입니다.

### 수강신청부터 바로, 규정을 더할수록 넓게

수강신청 안내문과 학칙은 이미 지식베이스에 들어 있어 **지금 바로 답할 수 있습니다.**
수강신청은 학년마다 신청일이 다르고(8/6·8/7·8/10·8/11), 다전공은 8/12 11~14시 딱 3시간,
교차수강은 잔여석 과목만, 정정기간에는 학과 이수제한이 풀리는 등 **학생이 "이 과목을 지금
신청할 수 있는가"조차 구분하기 어려운 영역**이라 첫 적용 대상으로 삼았습니다.

| 단계 | 추가할 규정 문서 | 새로 답할 수 있게 되는 질문 |
|---|---|---|
| 지금 | 학칙 · 수강신청 안내문 | 수강 가능 학점, 신청 일정, 휴학 요건, 성적 기준 |
| 다음 | 교과 정보(수강편람) · 학사운영규정 · 다전공 세칙 | 특정 과목의 이수제한·신청 대상, 복수전공 이수학점, 전과 기준 — 지금은 답하지 못하거나 인계하는 질문 |
| 이후 | 학과별 내규 · 졸업요건 · 장학 규정 | 졸업사정, 학과별 이수체계, 장학 자격 |

지식베이스는 수강신청 안내문을 바탕으로 구성해 **개별 과목의 교과 정보는 아직 없습니다.**
신청 일정은 답하지만 "이 과목을 지금 신청할 수 있는가"는 아직 답하지 못합니다.

시스템은 그대로 두고 **자료만 올리면 됩니다.** 적용 범위는 자료를 더하는 만큼 넓어집니다.

### 챗봇은 목적이 아니라 계측기다

이 프로젝트가 단순한 FAQ 챗봇과 다른 지점입니다.

**질문이 반복해서 몰리는 조항은 학생이 무지해서가 아니라 규정이 모호하기 때문입니다.**
답하지 못한 기록, 되묻는 질문, 조건을 오해한 질문이 모두 로그로 남아
**어느 조항을 개정해야 하는지** 가리킵니다.

```
질문 → 근거 검색 → 답변 · 인계 → 로그 적재 → 규정 개정 → 질문이 사라짐
```

챗봇은 질문에 **대응**하지만, 규정 개정은 질문을 **소멸**시킵니다.
전자는 운영이고 후자가 제도 개선입니다.

### 파이프라인

| 단계 | 내용 |
|---|---|
| 1. 수집 | 학칙 PDF를 브라우저에서 직접 파싱 |
| 2. 분할 | **제○조 단위**로 잘라 조문 하나가 검색 단위가 되게 함 |
| 3. 임베딩 | `text-embedding-3-small`로 벡터화 → Supabase 저장 |
| 4. 검색 | 코사인 유사도로 관련 조문 상위 6개. 임베딩이 없으면 글자 단위 부분 일치로 대체 |
| 5. 생성 | 선택된 조문 **원문만** 전달하고 그 밖의 내용은 말하지 말 것을 지시 |
| 6. 검증 | `answerable: false`면 답변을 표시하지 않고 인계. 인용 조항 실재 여부 대조 |
| 7. 규정 개선 | 질문 · 연결 조항 · 답변 가능 여부를 저장해 개정이 필요한 조항을 집계 |

> 학교 문서를 그대로 재배포하지 않기로 했습니다. `kb.json`과 원문 파일은 제외되어 있습니다.

## 실행

```bash
cd prototype-react
npm install
npm run dev
```

모델 호출은 두 가지 방식을 지원합니다.

- **직접 호출** — 화면에서 OpenAI API 키 입력. 키는 브라우저 localStorage에만 저장되며 코드에 포함되지 않습니다. 시연용.
- **Edge Function 경유** — 키가 Supabase 서버 시크릿에만 존재합니다. 배포용 권장.

자세한 배포 절차는 [`prototype-react/README.md`](prototype-react/README.md)를 참고하세요.

## 한계

**규정은 분석했으나 문의 로그는 확보하지 못했습니다.**
학칙 분석과 수강신청 안내문 분석은 실제로 수행한 결과입니다. 그러나 학사팀에 접수되는
문의 로그에는 접근 권한이 없어, 어떤 질문이 실제로 몇 건 들어오는지는 측정하지 못했습니다.

**환각을 0으로 만들 수는 없습니다.**
근거 기반 설계로도 오답 가능성은 0이 되지 않습니다.
그래서 되돌릴 수 없는 사안을 응답 범위에서 **의도적으로 제외**했습니다.
기술적 한계를 제도적 설계로 보완한 것입니다.

**규정 원문의 품질에 의존합니다.**
저장소의 규정이 최신이 아니면 시스템도 틀립니다.
갱신되지 않은 규정으로 답하는 것은 익명 커뮤니티와 같은 오류입니다.

**현재 권한 설정은 공개 시연용입니다.**
저장소는 읽기 전용으로 제한해 규정 데이터의 수정·삭제를 차단하고 질문 접수만 열어 두었습니다.
실제 운영에서는 **로그인 기반으로 관리자와 학생 권한을 분리**해 학사팀만 규정을 갱신하도록
설계했습니다. 규정 갱신 권한이 통제되지 않으면 답변의 신뢰도가 곧바로 무너지므로,
이 분리는 부가 기능이 아니라 **도입의 전제 조건**입니다.

**익명 커뮤니티를 대체하지는 못합니다.**
학생이 커뮤니티를 찾는 데에는 익명성과 접근성이라는 이유도 있습니다.
목표는 커뮤니티를 없애는 것이 아니라, 규정에 근거한 답이 필요한 질문에
**더 나은 선택지를 제공**하는 것입니다.

## AI 적용 과정과 활용 도구

공모 요강은 **AI 적용 과정·활용 도구·주요 결과·한계**를 최종 결과물에 명시하도록 요구합니다.
문제 발굴부터 시제품 구현까지 전 과정에 AI를 사용했습니다.

| 단계 | 활용 도구 | 구체적 내용 |
|---|---|---|
| ① 문제 발굴·정의 | 대화형 LLM (Claude) | 문제를 "응답 가능 시간의 공백 + 규정 문장의 모호성" 두 층위로 재정의, 반론 점검 |
| ② 문제 분석 *(활용범위 ①)* | Python 분석 스크립트 | 학칙 PDF 61쪽 → 조문 분해 → 위임 60건·단서 71건 계량, 조항별 모호성 순위 |
